# V1 vs V2 — the two API generations

Crawled on: 2026-09-28. V2 shapes are from the Classic Futures docs
(`04_trade.md`, `05_position.md`, `02_account.md`, `03_market.md`); V1 shapes
are reconstructed from Cachy's own call sites, because **V1 is no longer
documented anywhere on Bitget's site**.

## The finding

Every `/api/mix/v1/…` path answers HTTP `400`:

```json
{
  "code": "30032",
  "msg": "The V1 API has been decommissioned. Please migrate to a newer version.",
  "data": null
}
```

Verified live on 2026-09-28 against `api.bitget.com` from an unauthenticated
client. The same request in V2 returns `200`.

| Request | Result |
|---|---|
| `GET /api/mix/v1/market/candles?symbol=BTCUSDT_UMCBL&granularity=1m&limit=2` | `400` — `30032` |
| `GET /api/mix/v1/market/tickers?productType=umcbl` | `400` — `30032` |
| `GET /api/v2/mix/market/tickers?productType=USDT-FUTURES` | `200` |
| `GET /api/v2/mix/market/contracts?productType=USDT-FUTURES` | `200` |

**9 of the 10 REST call shapes Cachy makes are on V1 paths.** Only
`/api/v2/mix/market/contracts` is on V2 — the BUG-0501 fix, whose own code
comment already states the fact: *"V1 (/api/mix/v1/...) is decommissioned and
answers 30032, so this is V2 or nothing."*

## Why it survived so long

Three plausible reasons, all of them real:

1. **Bitget's own shipped SDK still contains it.**
   <https://github.com/BitgetLimited/V3-bitget-api-sdk> carries both
   `v1/mix/order_api.py` (posting to `/api/mix/v1/order/placeOrder`) and
   `v2/mix/order_api.py`.
2. **A separate Go SDK's README still demonstrates V1**, with an example that
   matches Cachy byte for byte: `side: "open_long"`,
   `timInForceValue: "normal"`, `symbol: "BTCUSDT_UMCBL"`,
   `WsUrl = "wss://ws.bitget.com/mix/v1/stream"`.
3. **Archived vendor docs still document V1**, including the V1 signing example
   with `requestPath = "/api/mix/v1/order/placeOrder"`.

So a developer copying from any of those sources produces working-looking code
against a dead API. The `code` inside the response is `"00000"` for success
elsewhere, and the SDK examples are internally consistent — nothing about
reading them suggests the path is dead.

The consequence for a reference like this one: **the vendor documentation is
not sufficient evidence that a Bitget endpoint works.** Only a live call is.
That is why every liveness claim in this set is dated and shows the request.

### Rows 7–9 are migrated (BUG-0576, 2026-09-30)

These are the three rows whose liveness needs no credentials, so they are now
recorded rather than assumed. Unauthenticated calls against `api.bitget.com`:

```
GET /api/v2/mix/market/candles?symbol=BTCUSDT&productType=USDT-FUTURES
    &granularity=1m&limit=2
→ 200 {"code":"00000","msg":"success","requestTime":1790782740000,
       "data":[["1790782740000","84128.2","84199.9","84123.8","84192.8",
                "22.4343","1888400.63673"]]}

GET /api/v2/mix/market/ticker?symbol=BTCUSDT
→ 400 {"code":"400172","msg":"Parameter verification failed","data":null}

GET /api/v2/mix/market/candles?symbol=BTCUSDT_UMCBL&productType=USDT-FUTURES
    &granularity=1m&limit=1
→ 400 {"code":"40034","msg":"Parameter BTCUSDT_UMCBL does not exist"}
```

Three things follow that the vendor documentation does not state:

1. **`productType` is required on the single-symbol `ticker` too**, not only on
   the list form. Omitting it is `400172`.
2. **The suffix has to be removed, not merely never appended.**
   `normalizeSymbol(s, "bitget")` still appends `_UMCBL` for thirty callers, so
   the venue strips it on the way out.
3. **Granularity names are unchanged** — `1m 5m 15m 30m 1H 4H 6H 12H 1D 1W 1M`
   plus `*utc` variants; lowercase `1h` is `400171`. The candle tuple is
   array-of-arrays exactly as in V1, so the parser body did not change.

The tickers carry a rename only the client sees, because `routes/api/tickers`
forwards Bitget's payload unparsed: `last`→`lastPr`,
`volume24h`→`baseVolume`, and `priceChangePercent` has no counterpart — V2's
`change24h` is a **fraction** (`0.01309` for +1.31%), so the change is derived
from `lastPr`/`open24h` rather than mapped across.

## ⚠️ The order schema changed shape, and a port that gets it wrong opens a position instead of closing one

This is the one place where a mechanical migration is actively dangerous.

### V1, what Cachy sends today

`side` is a single field carrying **both** the direction and whether the order
opens or closes. Four values:

```
open_long | open_short | close_long | close_short
```

Built by `bitgetSide()` at [`src/utils/exchange/bitgetBodies.ts:42`](../../src/utils/exchange/bitgetBodies.ts), which maps
Cachy's own `reduceOnly` + buy/sell pair onto those four.

### V2, what the venue wants

`side` and `tradeSide` are **separate fields**, and `side` now carries only the
position direction. From `00_common.md`, verbatim:

| Position mode | Parameters | Operation |
|---|---|---|
| One-way | `side: buy` / `side: sell` | buy / sell, `tradeSide` ignored |
| Hedge | `side: buy; tradeSide: open` | Opening a long position |
| Hedge | `side: sell; tradeSide: open` | Opening a short position |
| Hedge | `side: buy; tradeSide: close` | **Closing a long position** |
| Hedge | `side: sell; tradeSide: close` | **Closing a short position** |

### The failure mode

The V1 encoding decomposes losslessly into the V2 pair:

| V1 `side` | V2 `side` | V2 `tradeSide` |
|---|---|---|
| `open_long` | `buy` | `open` |
| `open_short` | `sell` | `open` |
| `close_long` | `buy` | `close` |
| `close_short` | `sell` | `close` |

So the correct port is a clean split-and-recombine. The danger is that
**`tradeSide` is the field that carries the close**, and it is the field a
mechanical port is most likely to drop:

> A close that is ported as `side: buy` with no `tradeSide` is not a rejected
> request and not a close. It is a valid **open long**. The position doubles
> instead of flattening, the order succeeds, and the only signal is the size.

This is why the migration cannot be a path-and-field rename reviewed by eye.
It needs a real hedge-mode account in a sandbox, and the acceptance test is
"position size returns to flat", not "request returned 200".

### One-way mode is a different problem again

In one-way mode Bitget **ignores `tradeSide` entirely** (see the table above).
There is therefore no way to express a close as open-versus-close; the close
has to come from `reduceOnly: YES` instead, with `side` carrying the
transaction direction.

So a V1 client that relied on `side` for both meanings may be relying on
`close_long` to close a long in a **hedge** account, and the equivalent V2
one-way request needs different fields entirely. Which mode the trader's
account is in is not something Cachy currently reads (see
`INTEGRATION_STATUS.md`), so the migration has to establish it before it can
pick a request shape.

**Unverified:** whether `reduceOnly` is accepted, required, or rejected in
hedge mode. The docs give no combination table. Needs a sandbox run.

### Do not carry V1's intuition into UTA

Worth stating because UTA is the family Bitget recommends and the next
migration target. UTA expresses the same intent with `posSide` instead of
`tradeSide` — and it inverts the transaction direction:

| | Classic V2 | UTA V3 |
|---|---|---|
| Open a long | `side: buy`, `tradeSide: open` | `side: buy`, `posSide: long` |
| **Close a long** | **`side: buy`**, `tradeSide: close` | **`side: sell`**, `posSide: long` |
| Open a short | `side: sell`, `tradeSide: open` | `side: sell`, `posSide: short` |
| **Close a short** | **`side: sell`**, `tradeSide: close` | **`side: buy`**, `posSide: short` |

Closing a long is `buy` on Classic and `sell` on UTA. A shared adapter that
normalises `side` once will silently invert every closing order across a
Classic↔UTA port. If the migration ever goes to UTA rather than V2, this table
is the thing to get wrong.

## Field-level deltas

### Place Order

| | V1 (Cachy today) | V2 |
|---|---|---|
| `symbol` | `BTCUSDT_UMCBL` | `BTCUSDT` — no suffix |
| `productType` | not sent | **required**, `USDT-FUTURES` |
| `marginMode` | not sent | **required**, `isolated` \| `crossed` |
| `marginCoin` | `USDT` | `USDT` |
| `side` | `open_long` \| `open_short` \| `close_long` \| `close_short` | `buy` \| `sell` — position direction |
| `tradeSide` | n/a | `open` \| `close`, hedge mode |
| `orderType` | `market` \| `limit` | `market` \| `limit` |
| `price` | required for limit | required for limit |
| `size` | `size` | `size` |
| time-in-force | `timInForceValue` (sic) | `force`: `ioc` \| `fok` \| `gtc` \| `post_only`, default `gtc` |
| `reduceOnly` | n/a — encoded in `side` | `YES` \| `NO` |
| `clientOid` | not sent | optional idempotency key |

V2 requires two fields Cachy does not send (`productType`, `marginMode`) and
rejects one it does (`timInForceValue`). A path-only port produces a `400`.

`timInForceValue` was never a Bitget V2 field at all — the misspelling is V1's.
It appears in stale doc samples, which is how it spreads.

### Query parameters

| | V1 | V2 |
|---|---|---|
| `productType` | `umcbl` | `USDT-FUTURES` |
| `symbol` | `BTCUSDT_UMCBL` | `BTCUSDT` |
| pagination | none on order lists | `idLessThan` + `endId` |
| `pageSize` | `pageSize`, Cachy clamps 1–100 | `limit`, max 100 |

Cachy appends the `_UMCBL` suffix in [`src/utils/symbolUtils.ts:60`](../../src/utils/symbolUtils.ts).
That helper exists solely for the V1 encoding and would have to go, not be
extended — the V2 contracts response returns `BTCUSDT` with no suffix, and
[`src/types/apiSchemas.ts:139`](../../src/types/apiSchemas.ts) already normalises that direction for the
one V2 call Cachy makes today.

### ⚠️ Query parameter ordering: unresolved

Cachy signs GET query strings in **insertion order, unsorted**
(`src/utils/crypto/exchangeSigning.ts:243`), and
[`src/utils/exchange/restSigningPlan.ts:202`](../../src/utils/exchange/restSigningPlan.ts) explicitly forbids applying the
sorted comparator to a Bitget route.

Bitget's own docs do the opposite. Every sample on the signature page — Java,
Python, JS — carries the comment *"Need to be sorted in ascending alphabetical
order by key"*, sorts before signing, and both worked examples come out
alphabetical. Details in `01_sign.md`.

**This cannot be settled from the documentation and cannot be settled from the
live V1 API, because V1 rejects every request before the signature is checked.**
It is the single most likely reason a signed Bitget `GET` has never worked, and
the most likely thing to be misdiagnosed as "the V1 decommission".

The safe assumption for the migration is that sorted is correct and the
insertion-order behaviour is a latent bug affecting every Bitget read. The
counter-consideration is only that the comparator is shared with Bitunix,
where sorted genuinely is required — so "it has always worked" is not available
as evidence for either side.

**A sandbox run against V2 must resolve this before any read path is
re-pointed.** Do not let a code review settle it.

### Response shapes

**Unverified in full.** V1 is no longer documented, so the V1 side of any
response delta can only be reconstructed from what Cachy's parsers read
(`venues/bitget.ts` L123-136, L163-177, L257-264, L379-391, L412-427), and a
parser that never ran is not a specification.

Known and certain:

- V2 signals success with `code: "00000"` inside an HTTP `200`, same as V1.
  Cachy already checks this.
- V2 order endpoints return `data: {orderId, clientOid}` for place/cancel, and
  `entrustedList` + `endId` for pending/history. Cachy reads `data` and iterates
  it directly, so a change from a bare list to an object is the likely breakage.

Everything else must be established by a live V2 call. This is the largest
unknown in the migration and the reason it cannot be a small PR.

## WebSocket is not a URL swap either

| | V1 (Cachy today) | V2 |
|---|---|---|
| Endpoint | `wss://ws.bitget.com/mix/v1/stream` | `wss://ws.bitget.com/v2/ws/public` **and** `wss://ws.bitget.com/v2/ws/private` |
| Sockets | one, carrying public and private | **two** |
| `instType` | `mc` | `USDT-FUTURES` \| `COIN-FUTURES` \| `USDC-FUTURES` |
| private `instId` | `default` | `default` (unchanged) |

Cachy's `bitgetWs.ts` deliberately runs a single socket and says so in a comment:
*"single socket, shared fate — when it goes down the authenticated stream goes
with it"*. That design decision is the one thing V2 does not allow. The
migration turns one lifecycle into two: two heartbeats, two reconnect
backoffs, two login lifecycles, and a new question about whether a partial
outage (public up, private down) is a state the UI has to represent.

Cachy's current `instType` value `mc` is the V1 spelling. The V2 docs document
`USDT-FUTURES` and show no `mc` variant anywhere — recorded here as a likely
second breakage rather than a confirmed one, since no V2 socket has been
dialled.

Timing constants in `bitgetWs.ts` (25 s ping against a 30 s recommendation and
a 2 min disconnect, 35 s watchdog) carry over unchanged. The 10 messages/second
ceiling and the 240 subscriptions/hour/connection cap do not become a problem
for a single-symbol client, but the refcount ledger is what keeps Cachy under
it and must be preserved per socket.

## What V2 adds that V1-shaped code cannot reach today

Three of these are answers to open backlog items, and they are the reason
migrating is worth more than restoring the status quo.

| Capability | V2 endpoint | Answers |
|---|---|---|
| Attached TP/SL on order entry | `presetStopSurplusPrice`, `presetStopLossPrice`, `presetStopSurplusExecutePrice`, `presetStopLossExecutePrice` on `place-order` | BUG-0503 — the unprotected window after opening a position |
| Native flash close | `POST /api/v2/mix/order/close-positions` | BUG-0514 — the bulk-close question |
| Cancel all orders | `POST /api/v2/mix/order/cancel-all-orders` | currently refused in `venueBodies.ts` |
| Batch place / batch cancel | `batch-place-order`, `batch-cancel-orders` (max 50) | currently refused |
| Order modify | `POST /api/v2/mix/order/modify-order` | currently refused |
| Mark-price candles | `kLineType: mark` on `candles`, plus `history-mark-candles` | `supportsMarkKlines: false` in [[`src/utils/server/venues/bitget.ts:519`](../../src/utils/server/venues/bitget.ts) |
| Leverage / margin / position mode | `set-leverage`, `set-margin`, `set-margin-mode`, `set-position-mode`, `set-auto-margin` | FEAT-0068 — all four currently return `null` |

Note that `set-leverage` and `set-margin-mode` return a field spelled
`shortLeveage`. A client that reads the documented field name gets nothing.
See `08_error_codes.md`.

Full reconciliation in `INTEGRATION_STATUS.md`.

## Migration order

Not a plan, just the dependency order the hazards above imply.

1. **Settle the query-ordering question** in a sandbox. It gates every read
   path and is cheap to test. Nothing else can be validated while signed GETs
   are of unknown correctness.
2. **Establish response shapes** by calling each V2 endpoint and recording what
   actually comes back. The parsers are written against V1, which no longer
   runs.
3. **Then the read paths** (rows 2, 3, 5, 6, 7, 8, 9) — mechanical once 1 and
   2 hold, and they unblock the position mirror that every close depends on.
4. **Then the write path** (rows 1, 4), with the order-schema split done
   deliberately and tested against a real hedge-mode account.
5. **Then the WebSocket split**, which is a lifecycle change rather than a
   schema change and should not be bundled with the REST port.
6. **Re-verify the capability flags** against V2's actual support. At least
   `tpSlAtEntry` has a verified shape to point at, and `positionModes` is
   non-empty in V2 (`one_way_mode` \| `hedge_mode`), so its current empty
   declaration should become a real answer.

Per BUG-0001, no step may be completed against a guessed wire format.
