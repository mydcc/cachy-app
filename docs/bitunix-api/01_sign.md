# Signature (Sign)

Source: https://www.bitunix.com/api-docs/futures/common/sign.html

## Restful API Signature – Public Parameters

### Headers

| Name        | Type   | Mandatory | Description                        |
|-------------|--------|-----------|-------------------------------------|
| `api-key`   | string | Y         | Requested API key                  |
| `nonce`     | string | Y         | `Random string，32bits` [sic — see note] |
| `timestamp` | string | Y         | Current timestamp, milliseconds  |
| `sign`      | string | Y         | Signature string                    |

> #### ⚠️ The `nonce` description is self-contradictory on the vendor's side
>
> The vendor writes, verbatim on the signature page: `Random string，32bits`
> (the comma is a fullwidth `，`). The introduction page says `random string,
> 32-bit, generated by the caller`. Neither mentions a charset or a character
> count, and **"32 bits" is not a length** — a 32-bit value is 4 bytes, or up to
> 8 hex digits.
>
> Bitunix's own samples contradict the stated width anyway. The REST signing
> samples in this very file use `nonce = "123456"` — six characters, at most
> ~20 bits. The WebSocket login example on the vendor's connect page uses a
> 32-character alphanumeric nonce. So the documented width, the REST samples and
> the WebSocket sample are three different things.
>
> **What is not in doubt:** the nonce is mandatory, on the REST header, on the
> WebSocket login frame, and in every private endpoint's `curl` sample. It is
> required in the prehash:
> `SHA256(nonce + timestamp + api-key + queryParams + body)`.
>
> **Practical guidance:** treat the nonce as an opaque caller-generated string
> and make it long and unique — its only real job is replay protection. Do not
> build a generator that targets a specific bit-width on the strength of this
> sentence; the sentence does not say what it appears to say.
>
> An earlier version of this file read *"32-char hex string (128-bit random)"*.
> That text had **no vendor source at all** — no page says "hex" or "128-bit" —
> and it was internally inconsistent besides, since 128 bits is 32 hex *digits*,
> not 32 characters. It appears to have been back-derived from the 32-character
> WebSocket example by counting characters.

### Signature steps

1. All `queryParams` are sorted ascending by the ASCII value of the key.
   Example: `String queryParams = "id1uid200"`
2. Body parameters are compressed into a string – **remove all spaces**. Example:
   `String body = {"uid":"2899","arr":[{"id":1,"name":"maple"},{"id":2,"name":"lily"}]}`
   > **Caution**: The request body format must match the signature string
   > exactly.
3. Signature – double encryption required:
   - `digest = SHA256(nonce + timestamp + api-key + queryParams + body)`
   - `sign = SHA256(digest + secretKey)`
   - Note: `secretKey` is issued together with the API key when applying. Store
     it securely, do not share it.

### Signature example (Go)

```go
package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

func main() {
	nonce := "123456"
	timestamp := "20241120123045"
	apiKey := "yourApiKey"
	secretKey := "yourSecretKey"
	queryParams := "id1uid200"
	body := "{\"uid\":\"2899\",\"arr\":[{\"id\":1,\"name\":\"maple\"},{\"id\":2,\"name\":\"lily\"}]}"

	digestInput := nonce + timestamp + apiKey + queryParams + body

	digest := sha256Hex(digestInput)

	signInput := digest + secretKey
	sign := sha256Hex(signInput)

	fmt.Println("Digest:", digest)
	fmt.Println("Sign:", sign)
}

func sha256Hex(input string) string {
	hash := sha256.Sum256([]byte(input))
	return hex.EncodeToString(hash[:])
}
```

### Signature example (Python)

```python
import hashlib

def sha256_hex(input_string):
    return hashlib.sha256(input_string.encode('utf-8')).hexdigest()

def main():
    nonce = "123456"
    timestamp = "20241120123045"
    api_key = "yourApiKey"
    secret_key = "yourSecretKey"
    query_params = "id1uid200"
    body = '{"uid":"2899","arr":[{"id":1,"name":"maple"},{"id":2,"name":"lily"}]}'

    digest_input = nonce + timestamp + api_key + query_params + body

    digest = sha256_hex(digest_input)

    sign_input = digest + secret_key
    sign = sha256_hex(sign_input)

    print("Digest:", digest)
    print("Sign:", sign)

if __name__ == "__main__":
    main()
```

> Always sign the exact serialized body string sent on the wire; pretty-printing invalidates the signature.

## WebSocket API Signature Parameters

WebSocket API requests require authentication. The following fields must be
included in all request parameters (`params`):

| Name        | Type   | Mandatory | Description       |
|-------------|--------|-----------|--------------------|
| `apiKey`    | string | Y         | API key            |
| `timestamp` | int    | Y         | Seconds format of Unix timestamp |
| `nonce`     | string | Y         | Random string      |
| `sign`      | string | Y         | Signature string    |

### Signature steps (WebSocket)

> **Cachy editorial, no vendor backing:** the note that this applies to
> `login` only, and that per-channel subscribe frames are unauthenticated, is
> **ours**. The vendor says only *"WebSocket API requests require
> authentication, and the following fields need to be included in all request
> parameter `params`"* — it never exempts subscribe. The reading is plausible,
> since the subscribe schema on the connect page carries no auth fields, but it
> is an inference and is marked as one.

1. Sort all fields in `params` except `sign` ascending by the ASCII value of the
   key, **remove all spaces**.
2. Signature – double encryption required:
   - `digest = SHA256(nonce + timestamp + apiKey + params)`
   - `sign = SHA256(digest + secretKey)`
   - Note: `secretKey` is issued together with the `apiKey` when applying. Store
     it securely, do not share it.

> #### ⚠️ Bitunix's two pages give two different WebSocket prehash formulas
>
> | Source | Formula |
> |---|---|
> | This page (`common/sign.html`) | `SHA256(nonce + timestamp + apiKey + params)` — **`params` included** |
> | The WebSocket connect page's Go sample | `sha256Hash(fmt.Sprintf("%s%d%s", nonce, timestamp, apiKey))` — **`params` omitted entirely** |
> | The WebSocket connect page's Python sample | `sha256Hash(nonce + str(timestamp) + api_key)` — **`params` omitted entirely** |
>
> Both code samples on the connect page hash only three values. One of Bitunix's
> two pages is wrong, and the docs do not say which. **Not resolved here.**
>
> This matters: this mirror carries both versions — the `params`-inclusive one
> above, and the `params`-omitting one in `08_websocket.md` (where the connect
> page's samples were transcribed). A reader implementing from
> `08_websocket.md` alone will produce signatures that this page contradicts.
>
> Note also what the REST formula omits: **the request path and the HTTP
> method are not prehash inputs.** The introduction page says GET parameters
> travel *"via queryString in the path"* — that describes transport, not the
> signature, and is easy to misread as "the path is signed". A consequence is
> that one signature is not bound to one endpoint.

#### ⚠️ The WebSocket login timestamp unit is also disputed

| Source | Says |
|---|---|
| The `timestamp` field table on this page | `Random string` for nonce; timestamp unit unstated here |
| WebSocket connect page, Login table | `Seconds format of Unix timestamp` |
| WebSocket connect page, Go sample | `time.Now().Unix()` — seconds |
| WebSocket connect page, Python sample | `int(time.time())` — seconds |
| WebSocket connect page, JSON example | `"timestamp": 1747402389` — 10 digits, seconds |
| The example string originally transcribed on **this** page | `timestamp1724285700000` — **13 digits, milliseconds** |

So the WebSocket unit is **seconds** on the dedicated WebSocket page in four
independent places, and the one example that says milliseconds lives on the
shared signature page. Seconds is the better-supported reading and is what the
REST/WS split implies. Recorded here because the contradicting string is still
in circulation.

#### ⚠️ The example string on this page is internally incoherent

`apiKey9a25209b66004da404d9ddcb48d1e11fnonce123456symbolBTCtimestamp1724285700000`

Three separate problems, all reproduced as found:

1. **`symbolBTC`** — the login request has no `symbol` field. The Login table
   and the login JSON example contain only `apiKey`, `timestamp`, `nonce` and
   `sign`. This appears to have been copied from a subscribe-shaped request.
2. **`timestamp1724285700000`** — 13 digits, milliseconds, against four sources
   saying seconds.
3. **`nonce123456`** — six characters, against the `32bits` in the header table.

The ASCII sort order (`apiKey` < `nonce` < `symbol` < `timestamp`) is correct.
The field set and the timestamp unit are not.

#### ⚠️ The REST samples use a non-epoch timestamp

Both REST signing samples on this page use `timestamp := "20241120123045"` —
14 digits in a `yyyyMMddHHmmss` pattern, not a 13-digit millisecond epoch. The
same page's header table says *"Current timestamp, milliseconds"*, and every
`curl` sample across this mirror uses `timestamp:1659076670000`. The vendor's
samples contradict the vendor's own stated unit. The samples are transcribed
verbatim; **do not copy them.**
