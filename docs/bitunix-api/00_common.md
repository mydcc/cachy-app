# API Introduction

Source: https://www.bitunix.com/api-docs/futures/common/introduction.html

## Overview

Welcome to the Bitunix API documentation. This OpenAPI documentation provides
a comprehensive guide to integrating with the Bitunix system: endpoints,
request/response formats, authentication requirements and
usage examples.

### OpenAPI Demo
Official demo (enter API key/secret to test):
https://github.com/BitunixOfficial/open-api

### Preparation for access

1. Log in at <https://www.bitunix.com/login>
2. Create an API key at <https://www.bitunix.com/account/apiManagement>
3. Note down after creation:
   - **APIKey**: identity for API transactions (randomly generated)
   - **SecretKey**: private key, randomly generated, used for signature creation

> ⚠️ **Risk warning**: These two keys are security-critical for your
> account. Never share them. If a leak is suspected, delete the API key immediately.

## Interface types

### Public Interface
Can be used for configuration information and market data.
Public requests require **no** authentication.

### Private Interface
Is used for order and account management. Every private request must
be signed (see `01_sign.md`), authentication via APIKey is
required.

## API Authentication

The header of every REST request must contain the following keys:

- `api-key`: API key of the request
- `nonce`: 32-char hex string (128-bit random), generated by the caller
- `timestamp`: current timestamp in milliseconds (REST; WS login uses seconds — see `08_websocket.md`)
- `sign`: signature string (see `01_sign.md`)
- `Content-Type`: uniformly `application/json`

## Interaction Request

All requests are based on HTTPS. The `Content-Type` in the POST request header
must be `application/json`.

### Flow
1. **Request parameters**: encapsulate the parameters according to the interface specification.
2. **Send request**: send the encapsulated parameters to the server via GET/POST.
3. **Server response**: the server first checks the parameter security and
   then returns the response data in JSON format.
4. **Data processing**: process the response data from the server.

### Success
HTTP status code `200` indicates a successful response (may contain content).

### Common error codes (HTTP)
- `400 Bad Request` – Invalid request format
- `403 Forbidden` – No access to the requested resource
- `404 Not Found` – No request found
- `500 Internal Server Error` – Internal server error; body may contain
  an error description

See `09_error_codes.md` for the complete list of business error codes.

## Standardised specification

### Timestamp
The timestamp in the request signature is given in milliseconds and
consistently refers to UTC time.

### Request formats
Currently there are only two request formats: GET and POST.

- **GET**: parameters are transferred via `queryString` in the path.
- **POST**: parameters are transferred in the body as JSON.
