# Backlog

Every planned unit of work — features, bugs, and ideas that are not yet either
— as one file each, with machine-readable front matter.

One item, one file, one ID. The ID never changes and never gets reused, so a
commit message, a branch name, a test comment or another item can point at it
permanently.

- **Index of everything:** [`INDEX.md`](INDEX.md) — generated, never edited by
  hand.
- **When things get built:** [`../ROADMAP.md`](../ROADMAP.md).
- **Why in that order:** [`../MILESTONES.md`](../MILESTONES.md).

---

## What goes where

This repository has three planning documents that are easy to confuse. The
difference is who has to act.

| Document | Holds | Acted on by |
| --- | --- | --- |
| [`../TODO.md`](../TODO.md) | Open **decisions** — a person has to choose before anything can be built | A human |
| **This backlog** | Planned **work** — what to build, specified enough to start | Anyone, human or agent |
| [`../ROADMAP.md`](../ROADMAP.md) | **Scheduling** — which backlog items belong to which release | Whoever plans |

A `TODO.md` entry becomes a backlog item once the decision in it is made. It
does not get copied: the backlog item links to the `TODO.md` section for the
full reasoning, and the reasoning stays in one place. The same rule applies to
`ARCHITECTURE.md`, the ADRs and the archived engineering log — **link, never
duplicate.** Two copies of a rationale is how documentation stops being true.

## File layout

```
backlog/
  features/FEAT-NNNN-short-slug.md
  bugs/BUG-NNNN-short-slug.md
  ideas/IDEA-NNNN-short-slug.md
  templates/
  INDEX.md          # generated by `npm run backlog:index`
```

Numbers are shared across all three types — there is no `FEAT-0001` and
`BUG-0001` at once. The next free number is whatever `INDEX.md` says plus one.

An `IDEA` that gets specified is **renamed** to `FEAT`, keeping its number:
`IDEA-0031-…` becomes `FEAT-0031-…`. The number is the identity; the prefix is
just its current state.

## Front matter

Every file starts with a YAML block. It is not decoration — `npm run
backlog:index` validates it and fails on anything unknown, so a typo in a status
is a failed check rather than an item that quietly vanishes from the index.

```yaml
---
id: FEAT-0001
title: Pre-flight order verification
type: feature
status: ready
priority: P0
milestone: M1
editions: [community, pro, private]
area: execution
data_class: A
adr: none
depends_on: []
---
```

| Field | Values | Meaning |
| --- | --- | --- |
| `id` | `FEAT-NNNN`, `BUG-NNNN`, `IDEA-NNNN` | Must match the filename |
| `title` | free text | One line, no trailing period |
| `type` | `feature`, `bug`, `idea` | Must match the `id` prefix and the directory |
| `status` | see below | Where it is |
| `priority` | `P0`–`P3` | See below |
| `milestone` | `M0`–`M9`, or `none` | From `MILESTONES.md` |
| `editions` | `community`, `pro`, `private` | Which builds get it (ADR-0003) |
| `area` | free slug | `execution`, `exchange`, `ui`, `alerts`, `ai`, … |
| `data_class` | `A`, `B`, `C`, `none` | Per ADR-0001 / ADR-0004. `none` = touches no data boundary |
| `adr` | `none`, `required`, or `ADR-NNNN` | `required` means it may not be built until one exists |
| `depends_on` | list of IDs | Hard blockers only, not "related to" |

### Status

`idea` → `specced` → `ready` → `in-progress` → `done`, or `dropped` at any point.

- **`idea`** — worth keeping, not thought through. No acceptance criteria yet.
- **`specced`** — the what and why are clear; acceptance criteria written.
- **`ready`** — an agent or a developer could start now: dependencies met, open
  questions resolved, required ADR exists.
- **`in-progress`** — someone is on it. Put the branch name in the item.
- **`done`** — merged **and** its acceptance criteria are proven, not just
  implemented. Record the version it shipped in.
- **`dropped`** — decided against. Keep the file and say why. A dropped item
  that gets re-proposed a year later should hit its own tombstone.

### Priority

- **`P0`** — money or security. An order that can go wrong, a credential that
  can leak, data that can be lost. Blocks a release.
- **`P1`** — a milestone's exit criterion depends on it.
- **`P2`** — wanted, scheduled, nothing breaks if it slips.
- **`P3`** — nice to have.

Priority is about consequence, not urgency. A cosmetic bug that has been
annoying for months is still `P3`.

## Body

The front matter is for machines; the body is for whoever builds it. Use
[`templates/feature.md`](templates/feature.md) or
[`templates/bug.md`](templates/bug.md).

Two sections are load-bearing and an item without them is not `ready`:

**Acceptance criteria.** Checkable statements. "Fast" is not one; "the check
runs before the transport call on every order path, proven by a test that adds a
bypassing call site and fails" is.

**Out of scope.** What this item deliberately does not do. This is what stops an
agent from helpfully expanding a two-hour task into a three-day one.

For bugs, `Evidence` replaces the feature sections: what was observed, and how
sure you are. This repository has an established discipline about that — see the
"a fix that compiles is not a bug that existed" entry in the archived
engineering log. **Say plainly whether the defect is demonstrated or only
derived from reading the code**, because that determines whether the fix needs a
reproducing test first.

## Working an item as an agent

1. Read the item, then read everything under `Links` in it. Do not start from
   the title alone.
2. Check `depends_on`. If a dependency is not `done`, stop and say so.
3. Check `adr`. If it is `required` and no ADR exists, the item is not
   buildable — write the ADR as its own pull request first.
4. Check `data_class`. Anything other than `none` means ADR-0001 and ADR-0004
   apply directly to your diff.
5. Set `status: in-progress` and note the branch, in the same commit as your
   first change.
6. Build it. Follow `CLAUDE.md` — Svelte 5 runes only, `decimal.js` for money,
   CSS variables for colour, tests beside the code.
7. Verify with the `/verify` skill: `npm run check` plus the affected tests.
   Report what actually ran and what it said.
8. Set `status: done`, record the shipped version, tick the acceptance criteria
   that are *proven*. Leave unproven ones unticked and say why.
9. Regenerate the index: `npm run backlog:index`.

**Do not silently change scope.** If the item is wrong, say so in the item and
ask — an item that turned out to be a bad idea is a useful finding. If it is
merely bigger than stated, split it into a new item rather than expanding this
one.

## Adding an item

```bash
cp docs/backlog/templates/feature.md docs/backlog/features/FEAT-0042-my-thing.md
# edit the front matter and body
npm run backlog:index
```

Nothing else. No approval step, no triage meeting — an unsorted item in the
backlog is better than an idea in a chat log. Set `status: idea` and
`priority: P3` if you are not sure; that is what those values are for.
